### 2.2 网络出口修复（根因）

- 现象：同样答案，Mac（住宅 IP）1~2 轮出票，服务器 40+ 轮 0 出票。
- 取证：服务器是 PVE 宿主机（10.21.76.202）上的 `dag2.0-backend` 虚拟机；
  VPN 不在宿主机（宿主机出口广东电信，干净），而在 iStoreOS 网关
  （10.21.76.16，VMID 101，OpenClash TUN 透明代理），出口新加坡。
- 机制：TUN + fake-IP（198.18.x）让 `GEOIP,CN→Direct` 永远匹配不上，
  实际≈全局走 VPN；TCP 建连 0.6ms（本地终结）证实透明代理。
- 修复：iStoreOS `custom/openclash_custom_rules.list` 加 6 条腾讯验证码/
  微信读书域名 `DOMAIN-SUFFIX → DIRECT`（备份 `.bak-20261017`），重启生效；
  其余流量零变化。生效后**连续 3 次首轮出票**（15~26 秒），双账号恢复 HEALTHY。

### 2.3 无 ADB 模式

- 服务器 `config.yaml`：`adb.enabled: false`（手机离线，AAOS 无障碍链与 ADB
  坐标管线全部停用；`AdbDeviceSupervisor` 不再探查重试）。
- Web 通道：健康检查每 5 分钟一轮；凭证过期时生成新二维码并推送企微+飞书，
  服务端轮询 `getLoginInfo` 等待人工扫码，扫码成功即恢复采集，失败退避后下轮
  发新码。人工扫码是当前唯一恢复路径（手机上线前）。
- E-Ink 通知策略：`sendEinkManualFallback` 遇 `RECOVERED` 直接返回——自动
  解题成功时不发任何机器人消息（15:38/11:11/11:12 三次成功窗口日志实证）；
  仅解题失败/未配置时才发人工验证链接+二维码。

## 4. Web 二维码链接复用加刷新页（2026-10-17 16:45 上线，已验证）

- 背景：无 ADB 后每 5 分钟健康检查生成新码并双机器人推送，消息过多。
- 改为 E-Ink 模式：有效期内（`weread.qr_reuse_window_seconds`，默认 300s）
  复用同一扫码链接；同账号等待扫码期间机器人提醒限频
  （`weread.qr_reminder_interval_seconds`，默认 3600s）；失败提醒同样限频，
  同账号单位间隔内最多一条登录相关消息。
- 新增刷新页 `GET /weread/web/login/refresh?vid=`（状态+二维码图+剩余有效期+
  “重新获取二维码”按钮）与一键续期接口
  `POST /api/weread/account/recover/refresh?vid=`（强制换新码并推送，同时唤醒轮询）；
  机器人二维码消息附带刷新页链接；Nginx 加两条精确路径代理（`/weread/web/login/`、
  `/api/weread/account/recover/refresh`，其余 `/api/` 仍走 21001）。
- 验证：刷新页正常渲染（含二维码图/倒计时/按钮）；刷新接口强制换新码并推送；
  轮询按 60 秒分轮，续期自动被接走。

## 5. 死信盘点结论：234 条全部暂不可服务端处理（2026-10-17 18:30）

- 抽样 100 条全部是同一回填任务（job 6469278，gzhName=海珠检查，21 天窗口，
  2024-06～2025-07），失败原因全是 `ACCOUNT_LOOKUP_UNAVAILABLE`。
- 根因链：任务名“海珠检查”在本地订阅库无记录（库里只有“海珠检察”等），而
  主微信通道永久禁用（ret=200013），服务端无法解析账号 → 只能死信给手机。
- 关键发现：死信里的二维码图解出 `weixin.qq.com/r/mp/...` 关注链接，图面为
  “广州海珠发布”（本地库有该订阅，E-Ink 可覆盖）；手机今早实际采的也是该号
  列表——任务名与二维码指向错位。
- 小批量改名回灌（3 条）证明服务端能走通订阅→缓存→E-Ink 链路，但暴露真 bug：
  `PublicAccountCollectionCheckpoint.covers()` 把 `oldest=0`（未知）当成
  “自 1970 全覆盖”，26/28 个检查点受影响，历史窗口 0 篇误判 complete。
- 已补救：删除 3 行毒化覆盖记录，原样补回 3 条死信（DLQ 回到 234 条）；
  上游 3 条 EMPTY 结果无法撤回，已记录待上游知悉。
- 已修复并上线：`covers()` 要求 `oldest > 0`（附回归测试，140 通过）。
- 结论：在手机上线前，**不要批量回灌**——E-Ink 到不了 2024 纵深历史，
  误判 complete 比积压更有害；死信等手机消化是正确路径。

## 6. PROBE_FAILED 自动重试（2026-10-17 17:30 上线）

- 现象：解题器出票正常（腾讯 errorCode=0），但 938161607 的提交后恢复探测
  偶发失败（`PROBE_FAILED`），每次失败都发一条人工兜底消息；909705585 则稳定恢复。
- 根因：票据有效，恢复探测（带票据的真实 API 请求）对该账号偶发仍返回 -2041；
  手动隔几分钟重试一次往往就过——属服务端状态传播/风控波动，非解题器故障。
- 修复（`WeReadEinkRuntime.performEinkAutoRecovery`）：单次尝试内对
  `PROBE_FAILED`（及偶发 `SOLVE_FAILED`）等待 30 秒后用新挑战再打一轮，
  最多 2 个周期，累计 attempts/duration 上报；仅基础设施类错误直接返回。
  单测 `WeReadEinkAutoRecoverySmokeTest` 已同步更新（128 通过）。
- 预期效果：偶发探测失败在同一次尝试内自愈，不再为此发机器人消息。
