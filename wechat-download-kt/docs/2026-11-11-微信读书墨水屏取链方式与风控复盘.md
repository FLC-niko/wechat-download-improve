> 日期：2026-11-11
> 现场设备：Xiaomi 22041216C（Android 14，序列号 `M7Z5HABUMJT8BUO7`）
> 微信读书墨水屏版：`com.tencent.weread.eink` 2.1.2（versionCode 10245900）
> 服务端：`topview@10.21.76.61`，部署标签 `kt-166123b40ca2`
> 本文只记录链路与风控结论，已隐去 `accessToken`、`pass_ticket`、`exportkey` 等会话凭据。

## 0. 结论摘要

1. **墨水屏 App 获取公众号文章链接的核心方式是“列表接口直出”，不是逐篇抓文章页。**
   - 接口：`GET https://i.weread.qq.com/mp/chapters?bookId=<公众号在微信读书内的ID>&count=50`
   - 返回：`data[]`，每项含 `reviewId`、`createTime`、`mpInfo`；`mpInfo` 中带 `doc_url`（完整 `https://mp.weixin.qq.com/s?...`）或 `originalId`。
   - 翻页：滚动加载时用 `offset`，不是拿列表里的 `synckey` 回传。
   - 时间范围：客户端按每条的 `createTime` 过滤，不需要额外接口。
2. **App 列表路径没有证据显示会逐篇调用 `/review/single`。** 项目本地只有在链接字段都无法映射时才做回填；`review_single_backfills` 统计实际回填调用尝试，不再用 `skipped` 代替。
3. 只读数据库抽样当时有 **16,352 条 source=eink 的文章行**，其中 **15,744 条完整查询链接**，608 条短链。行数不能当作唯一文章数，URL 形态和重复身份可能有差异。
4. **手机与 APK 证据支持**列表读取、每页50和 offset 翻页等实现线索；实际响应字段、`clearAll` 和分页结束语义仍需真实响应验证。合成响应测试不构成线上协议证据。
5. **风控需区分已观测现象与因果假设。**
   - 手机 App 登录的 `vid=909705585` 与服务器 E-Ink 正在使用的 `vid=909705585` 相同；观测到同一账号在两个客户端使用，但现有观测不能证明它造成了风控。
   - Web 账号 `938278172` 有 `-2041`、自动解题恢复和后续频控空列表日志；快照时累计频控计数为 213。
   - E-Ink `909705585` 在 2026-11-10 23:19 左右出现 `-2041` 并进入人工验证静默，稍后又有同步完成日志。另一个 E-Ink `938161607` 的 `232` 是失败计数，不是 232 个验证周期；失败计数和成功率不能证明设备/账号之间的因果关系。
6. **建议优先做三件事**：
   - 账号隔离作为可回滚运维选项：先备份 `909705585` 对应的两类凭证和遗留单账号文件，确认独立账号可用后再评估切换；避免启动时自动迁回旧文件。本次不移动凭证、不重启服务。
   - 任务按时间范围截断分页：命中 `createTime <= 目标开始时间` 立即停止；不要每次任务都全量回扫历史。
   - 人工确认 Web `-2041` 恢复后立即重新调度；只有新发生的 `-2014` 才使用 1200 秒频控冷却。频控空列表仍不得视为覆盖完成。

## 2. App 取链链路（反编译证据）

反编译 APK（jadx 1.5.1）后，关键类如下：

| 类 / 方法 | 作用 | 关键代码/字段 |
|---|---|---|
| `com.tencent.weread.ds.mp.MpRemoteService` | 公众号列表远端服务 | `PATH_GET_CHAPTERS = "/mp/chapters"`；`PATH_GET_LIST = "/mp/list"`；`PATH_GET_REVIEW = "/review/single"` |
| `MpRemoteService$syncChapters$2` | 首次拉列表 | `GET /mp/chapters`，参数只有 `bookId`、`count` |
| `MpRemoteService$loadMoreChapters$2` | 滚动翻页 | `GET /mp/chapters`，参数 `bookId`、`count`、`offset` |
| `MpChapterList` | 列表响应 | `synckey`、`data: List<MpChapterItem>`、`clearAll` |
| `MpChapterItem` | 单条文章 | `reviewId`、`createTime`、`mpInfo: SimpleMpInfo` |
| `SimpleMpInfo` | 列表里的公众号信息 | `title`、`pic_url`、`payType`（列表模型不解析 `doc_url`） |
| `MpInfo`（详情模型） | 文章详情 | `@JSONField(name="doc_url") private String url`；另有 `originalId`、`title`、`time` |
| `MpRemoteService$getReviewMpInfo$2` | 单篇详情 | `GET /review/single?reviewId=...` |
| `MpService` | 本地缓存/同步 | `GET_CHAPTER_CNT = 50`；本地 `LocalMpChapters(data, count, hasMore)` |
| `StoryDetailTopMpController` | 打开文章 | `str = mpInfo.getUrl()`，用 `doc_url` 加载 WebView |
| `StoryDetailMpFragment` | 目录/离线缓存 | 懒加载 `singleReviewService.loadReviewByReviewId(reviewId)` |

### 2.1 列表请求

`MpRemoteService$syncChapters$2`：

```java
URLBuilder uRLBuilder = new URLBuilder(URLProtocol.INSTANCE.getHTTPS(),
        ReadHost.SERVICE_USER_HOST, ...);
URLBuilderKt.setEncodedPath(uRLBuilder, MpRemoteService.PATH_GET_CHAPTERS);
ClientExKt.addParam(uRLBuilder, "bookId", str);
ClientExKt.addParam(uRLBuilder, "count", Boxing.boxInt(i3));
```

即：

```http
GET /mp/chapters?bookId=<bookId>&count=50
```

`loadMoreChapters` 额外加 `offset`，没有加 `synckey`：

```http
GET /mp/chapters?bookId=<bookId>&count=50&offset=<offset>
```

`MpChapterList` 的响应字段：

```java
private final boolean clearAll;
private final List<MpChapterItem> data;
private final long synckey;
```

`clearAll` 字段存在，但它对列表覆盖、清空或分页终止的具体语义未通过真实响应确认；本地解析只保存该 nullable 值作观察。

`MpChapterItem`：

```java
private final long createTime;
private final SimpleMpInfo mpInfo;
private final String reviewId;
```

### 2.2 链接从哪里来

列表模型 `SimpleMpInfo` 只解析 `title/pic_url/payType`，但原始 JSON 的 `mpInfo` 里还有 `doc_url` / `originalId`。服务端代码 `WeReadEinkChaptersClient.parseMpInfo` 已经按这些字段解析：

```kotlin
originalId = stringField(obj, "originalId"),
docUrl = stringField(obj, "doc_url"),
...
```

打开文章时，App 使用详情模型 `MpInfo.getUrl()`（对应 JSON `doc_url`）加载 WebView；如果列表没有 `doc_url`，就用 `reviewId` 还原短链：

```kotlin
fun shortLinkFromReviewId(reviewId: String): String? {
    // MP_WXS_<uin>_<token> -> https://mp.weixin.qq.com/s/<token>
}
fun articleUrlFromOriginalId(originalId: String): String? {
    // 支持完整 URL、/s 开头、__biz=... 查询串、纯 token
}
```

因此取链有优先级：

```text
mpInfo.doc_url
  > 已缓存 link
  > reviewId 还原 https://mp.weixin.qq.com/s/<token>
  > mpInfo.originalId 还原
  > 必要时 /review/single 补全
```

### 2.3 时间范围

App 列表项带 `createTime`（秒级时间戳）。时间范围筛选是客户端逻辑：按列表倒序翻页，命中 `createTime <= 目标开始时间` 后即可停止；不需要按时间调用额外接口。

### 4.3 关键风险点

1. **同一 vid 被手机和服务器同时使用**：手机 App 数据库路径是 `databases/909705585/...`；服务器 E-Ink 的 `active_vid` 也是 `909705585`。这是需控制验证的混杂因素，目前没有因果证据。
2. **Web 兜底的观测现象**：历史日志里曾有 `-2041` 自动恢复后接着出现 `offset=0` 频控空列表；该顺序不能证明延长恢复等待有帮助。新验证成功后立即恢复调度，新 `-2014` 仍按独立频控冷却处理。
3. **E-Ink 全量回扫过多**：单次任务常见 `pages=3/5/6/10`，`fetched=200~495`；对“某段时间”任务来说，命中起始时间后应立刻停止，而不是继续把历史翻完。
4. **`mobileSync` 激活从未使用**：日志中 `mobileSync` 为 0 行，配置 `mobile_sync_activation.enabled=false`；不能从此推断启用它能降低风控。

## 5. 收益判断

### 5.1 已经确认的收益

- **取链方式观察**：APK与本次已有观测支持从 `/mp/chapters` 列表获取文章标识和链接字段；实际响应字段仍需fixture验证，不能据此断言每种返回都无需回填。
- **不需要手机 UI 自动化**：手机 App 的“目录”列表本质上也是 `/mp/chapters`，用服务器 API 复现即可，没必要用无障碍点击。
- **不需要 `pass_ticket`**：`pass_ticket` 只是微信 WebView 的会话票据，不能复用到服务器；链接本体不含它也能访问。
- **分页实现方向**：首屏请求、offset续页和按 `createTime` 截断都由代码支持；`hasMore`、`nextOffset`与结束语义需真实响应核实。

### 5.2 可进一步获得的收益

- **降低请求量**：按目标任务的时间范围截断，通常 1–2 页即可覆盖一个月，避免每次 5–10 页。
- **降低 `-2041` 概率**：App 的请求节奏是“打开目录时拉一页，滚动再拉下一页”，不是后台连续翻 10 页；把服务器同步改成“按需分页 + 长间隔”更接近真实行为。
- **设备身份隔离**：如果服务器必须用 E-Ink，最好给服务器一个独立的 vid/设备身份；不要和手机共用 909705585。
- **`mobileSync` 可选实验**：在独立账号上开启 `mobile_sync_activation`，模拟 App 启动时的终端激活，可能降低 `-2041`；但必须小范围、可回滚，不能全局打开。

## 6. 降低风控的可执行建议

### P0（优先做，风险最低）

1. **一 vid 一客户端**
   - 手机 App 使用 `909705585`；
   - 服务器 E-Ink 改用另一个独立账号（例如恢复 `938161607`，或新开第三个墨水屏账号）；
   - 不要在服务器和手机同时跑同一个 vid；如果必须共用，至少保证同一时间只有一个客户端在请求。
2. **任务按时间范围截断**
   - 命中 `createTime <= 目标开始时间` 立即停止翻页；
   - 后台历史扫描仍可用 `max_pages: 1000`；实时补链另有 `targeted_max_pages: 20` 预算；
   - 优先命中本地缓存和覆盖度，不要每次任务都全量回扫。
3. **不要为整个列表逐篇 `/review/single`**
   - 继续使用列表里的 `doc_url` / `originalId` / `reviewId`；
   - `doc_url` 缺失时先尝试缓存、`originalId` 与 `reviewId`短链；仍无法映射才调用 `/review/single`；
   - 用 `review_single_backfills` 观察实际调用，不用 `skipped` 推断调用数。

### P1（建议尽快做）

4. **Web验证恢复与频控分别处理**
   - 人工确认 `-2041` 已恢复后立即重新调度，不再加恢复等待或额外探测门槛；
   - 新发生的 `-2014` 使用本地 `freq_control_cooldown: 1200`；
   - 频控返回的空列表不能当作“覆盖完成”，应标记为未覆盖并走 E-Ink/缓存。
5. **E-Ink 请求节奏**
   - `weread.eink.min_request_interval` 本地值设为 10 秒（代码仍有硬下限和随机长停顿）；
   - 避免健康探测和后台同步在同一 vid 上紧邻发生；
   - `-2041` 后 E-Ink 真实探测间隔本地设为 7200 秒；Web 验证成功后立即恢复调度，后续 -2014 仍按现有冷却策略处理。
6. **分页参数与 App 对齐**
   - 首次无历史游标请求 `bookId + count`；有效增量游标继续使用 `synckey`；
   - 需要翻页时用 `offset`；
   - 只有在确认 `synckey` 增量语义可靠时才使用增量同步。

### P2（需要小范围验证）

7. **`mobileSync` 终端激活实验**
   - 仅在独立 E-Ink 账号上开启，`vid_allowlist` 只放该账号；

## 8. 不建议做的事

- **不要把 `pass_ticket` / `exportkey` 写入配置或数据库**：它们是微信会话票据，短时有效且高敏。
- **不要用手机无障碍去逐篇点开文章取链接**：列表接口已经直出链接，UI 自动化只会更慢、更容易触发风控。
- **不要在同一个 vid 上同时跑服务器同步和手机 App**：这是当前最可疑的风控触发源之一。
- **不要用“频控空列表”判定覆盖完成**：会把缺口误标成 EMPTY，后续任务不再回源。
- **不要把 `mobile_sync_activation` 全局打开**：先用独立账号 + allowlist 做 A/B，观察 `-2041` 和成功率后再决定。
