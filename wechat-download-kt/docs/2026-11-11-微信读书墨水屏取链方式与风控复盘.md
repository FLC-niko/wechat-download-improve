## 0. 结论摘要

1. **墨水屏 App 获取公众号文章链接的核心方式是“列表接口直出”，不是逐篇抓文章页。**
   - 接口：`GET https://i.weread.qq.com/mp/chapters?bookId=<公众号在微信读书内的ID>&count=50`
   - 返回：`data[]`，每项含 `reviewId`、`createTime`、`mpInfo`；`mpInfo` 中带 `doc_url`（完整 `https://mp.weixin.qq.com/s?...`）或 `originalId`。
   - 翻页：滚动加载时用 `offset`，不是拿列表里的 `synckey` 回传。
   - 时间范围：客户端按每条的 `createTime` 过滤，不需要额外接口。
2. **App 列表路径没有证据显示会逐篇调用 `/review/single`。** 项目本地只有在链接字段都无法映射时才做回填；`review_single_backfills` 统计实际回填调用尝试，不再用 `skipped` 代替。
3. 只读数据库抽样当时有 **16,352 条 source=eink 的文章行**，其中 **15,744 条完整查询链接**，608 条短链。行数不能当作唯一文章数，URL 形态和重复身份可能有差异。
4. **手机与 APK 证据支持**列表读取、每页50和 offset 翻页等实现线索；实际响应字段、`clearAll` 和分页结束语义仍需真实响应验证。合成响应测试不构成线上协议证据。
5. **风控需区分已观测现象与因果假设。**
   - 手机 App 登录的 `vid=909705585` 与服务器 E-Ink 正在使用的 `vid=909705585` 相同；观测到同一账号在两个客户端使用，但现有观测不能证明它造成了风控。
   - Web 账号 `938278172` 有 `-2041`、自动解题恢复和后续频控空列表日志；快照时累计频控计数为 213。
   - E-Ink `909705585` 在 2026-11-10 23:19 左右出现 `-2041` 并进入人工验证静默，稍后又有同步完成日志。另一个 E-Ink `938161607` 的 `232` 是失败计数，不是 232 个验证周期；失败计数和成功率不能证明设备/账号之间的因果关系。
6. **建议优先做三件事**：
   - 账号隔离作为可回滚运维选项：先备份 `909705585` 对应的两类凭证和遗留单账号文件，确认独立账号可用后再评估切换；避免启动时自动迁回旧文件。本次不移动凭证、不重启服务。
   - 任务按时间范围截断分页：命中 `createTime <= 目标开始时间` 立即停止；不要每次任务都全量回扫历史。
   - 人工确认 Web `-2041` 恢复后立即重新调度；只有新发生的 `-2014` 才使用 1200 秒频控冷却。频控空列表仍不得视为覆盖完成。

## 2. App 取链链路（反编译证据）

反编译 APK（jadx 1.5.1）后，关键类如下：

| 类 / 方法 | 作用 | 关键代码/字段 |
|---|---|---|
| `com.tencent.weread.ds.mp.MpRemoteService` | 公众号列表远端服务 | `PATH_GET_CHAPTERS = "/mp/chapters"`；`PATH_GET_LIST = "/mp/list"`；`PATH_GET_REVIEW = "/review/single"` |
| `MpRemoteService$syncChapters$2` | 首次拉列表 | `GET /mp/chapters`，参数只有 `bookId`、`count` |
| `MpRemoteService$loadMoreChapters$2` | 滚动翻页 | `GET /mp/chapters`，参数 `bookId`、`count`、`offset` |
| `MpChapterList` | 列表响应 | `synckey`、`data: List<MpChapterItem>`、`clearAll` |
| `MpChapterItem` | 单条文章 | `reviewId`、`createTime`、`mpInfo: SimpleMpInfo` |
| `SimpleMpInfo` | 列表里的公众号信息 | `title`、`pic_url`、`payType`（列表模型不解析 `doc_url`） |
| `MpInfo`（详情模型） | 文章详情 | `@JSONField(name="doc_url") private String url`；另有 `originalId`、`title`、`time` |
| `MpRemoteService$getReviewMpInfo$2` | 单篇详情 | `GET /review/single?reviewId=...` |
| `MpService` | 本地缓存/同步 | `GET_CHAPTER_CNT = 50`；本地 `LocalMpChapters(data, count, hasMore)` |
| `StoryDetailTopMpController` | 打开文章 | `str = mpInfo.getUrl()`，用 `doc_url` 加载 WebView |
| `StoryDetailMpFragment` | 目录/离线缓存 | 懒加载 `singleReviewService.loadReviewByReviewId(reviewId)` |

### 2.1 列表请求

`MpRemoteService$syncChapters$2`：

```java
URLBuilder uRLBuilder = new URLBuilder(URLProtocol.INSTANCE.getHTTPS(),
        ReadHost.SERVICE_USER_HOST, ...);
URLBuilderKt.setEncodedPath(uRLBuilder, MpRemoteService.PATH_GET_CHAPTERS);
ClientExKt.addParam(uRLBuilder, "bookId", str);
ClientExKt.addParam(uRLBuilder, "count", Boxing.boxInt(i3));
```

即：

```http
GET /mp/chapters?bookId=<bookId>&count=50
```

`loadMoreChapters` 额外加 `offset`，没有加 `synckey`：

```http
GET /mp/chapters?bookId=<bookId>&count=50&offset=<offset>
```

`MpChapterList` 的响应字段：

```java
private final boolean clearAll;
private final List<MpChapterItem> data;
private final long synckey;
```

`clearAll` 字段存在，但它对列表覆盖、清空或分页终止的具体语义未通过真实响应确认；本地解析只保存该 nullable 值作观察。

`MpChapterItem`：

```java
private final long createTime;
private final SimpleMpInfo mpInfo;
private final String reviewId;
```

### 2.2 链接从哪里来

列表模型 `SimpleMpInfo` 只解析 `title/pic_url/payType`，但原始 JSON 的 `mpInfo` 里还有 `doc_url` / `originalId`。服务端代码 `WeReadEinkChaptersClient.parseMpInfo` 已经按这些字段解析：

```kotlin
originalId = stringField(obj, "originalId"),
docUrl = stringField(obj, "doc_url"),
...
```

打开文章时，App 使用详情模型 `MpInfo.getUrl()`（对应 JSON `doc_url`）加载 WebView；如果列表没有 `doc_url`，就用 `reviewId` 还原短链：

```kotlin
fun shortLinkFromReviewId(reviewId: String): String? {
    // MP_WXS_<uin>_<token> -> https://mp.weixin.qq.com/s/<token>
}
fun articleUrlFromOriginalId(originalId: String): String? {
    // 支持完整 URL、/s 开头、__biz=... 查询串、纯 token
}
```

因此取链有优先级：

```text
mpInfo.doc_url
  > 已缓存 link
  > reviewId 还原 https://mp.weixin.qq.com/s/<token>
  > mpInfo.originalId 还原
  > 必要时 /review/single 补全
```

### 2.3 时间范围

App 列表项带 `createTime`（秒级时间戳）。时间范围筛选是客户端逻辑：按列表倒序翻页，命中 `createTime <= 目标开始时间` 后即可停止；不需要按时间调用额外接口。

### 2.4 补充：微信主程序 8.0.76 点开公众号时如何批量拉历史文章

实测微信主程序（`com.tencent.mm` 8.0.76）点开公众号后，进入的是 **原生公众号主页** `ContactInfoUI`，不是旧版 WebView。页面顶部有“全部 / 贴图 / 文章 / 视频号 / 服务”标签，向下滚动时按日期分批加载历史文章；实测滚动后依次出现 `10月30日`、`10月29日`、`10月28日` 的历史条目。

反编译 `classes14.dex` 的 `com.tencent.mm.plugin.profile.ui.tab.data.BizProfileDataFetcher` 可以看到实际请求：

```java
// 首次进入公众号主页
lVar.d = 2656;
lVar.c = "/cgi-bin/mmbiz-bin/bizattr/bizprofilev2";
xlVar.e = 0;      // 起始偏移
xlVar.g = 5;      // 首次只取 5 条消息（一次群发可能包含多篇文章）

// 向下滚动加载更多
lVar3.d = 2656;
lVar3.c = "/cgi-bin/mmbiz-bin/bizattr/bizprofilev2";
xlVar.e = i;      // 当前偏移
xlVar.f = gVar;   // 游标（上一页最后一条）
xlVar.g = 20;     // 每次 20 条消息
```

如果是“作者/MP 身份”场景，走另一个命令：

```text
cmdId = 28057
path  = /cgi-bin/mmbiz-bin/bizattr/bizprofilev2mp
```

反编译中还能直接看到响应/数据模型：

```text
BizProfileV2Resp
AffBizMessage
BizProfileTabMsgFragment       // “全部”
BizProfileTabArticleFragment  // “文章”
BizProfileTabPicFragment      // “贴图”
BizProfileTabVideoFragment    // “视频号”
MsgList
MsgList.FeaturedList
AppmsgTab.MsgList
AudioTab.MsgList
PicTab.MsgList
```

也就是说，微信主程序的历史文章是**按标签、按页（首次 5 条消息，之后 20 条消息）从 `bizprofilev2` 原生 CGI 拉取**，返回的是 protobuf 的 `AffBizMessage` 列表；每条消息里带 `appMsg` / `detailInfo`（一次群发可包含多篇文章），文章链接仍然是 `content_url`（`mp.weixin.qq.com/s?...`）。

另外，`classes8.dex` 里仍保留旧版网页历史入口的字符串：

```text
/mp/profile_ext?
/mp/appmsg/show
/mp/appmsgalbum?
/showappmsg?
```

旧版/部分入口的 `profile_ext` 历史页经典做法是：

```http
GET https://mp.weixin.qq.com/mp/profile_ext?action=home&__biz=<biz>&scene=<scene>
GET https://mp.weixin.qq.com/mp/profile_ext?action=getmsg&__biz=<biz>&f=json
    &offset=<offset>&count=10&is_ok=1&scene=<scene>
    &uin=<uin>&key=<key>&pass_ticket=<pass_ticket>
```

返回 `general_msg_list`，里面是 `comm_msg_info` + `app_msg_ext_info`，每篇的 `content_url` 就是文章链接。这个接口需要登录态 `key/pass_ticket/uin`，且是微信重点风控对象；本次没有用它做批量抓取。

**对我们的意义**：

- 微信主程序走的是**原生 MMTLS + protobuf `bizprofilev2`**，不是公开 HTTP API；服务器无法像调用微信读书 `/mp/chapters` 那样直接复用。
- 旧版 `profile_ext/getmsg` 虽然理论上可复制，但需要真实微信登录态，且更容易触发风控；不如继续用微信读书 E-Ink 列表。
- 项目现有主微信通道用的是公众号后台 `appmsgpublish`（已因 `200013` 停用），它和读者侧 `bizprofilev2` / `profile_ext` 不是同一条链路；`200013` 不能直接推断读者侧历史接口也不可用，但后者需要真实微信登录态 + MMTLS，服务器侧实现和风控成本都更高。
- 微信主程序的“首次 5 条消息 + 后续 20 条消息”说明它也是**懒加载、按需分页**，不是一次拉全量；这与我们建议的“按时间范围截断 + 少量分页”一致。

### 2.5 关于“模拟微信官方会话”和 Linux 微信 hook 的可行性

**结论：不能承诺“稳定不触发人工验证码”。**

原因：

- 微信风控不是只看协议/UA，还会看账号历史、设备指纹、登录地点/IP、行为节奏、是否新设备、是否多设备并发。即使协议层完全模拟官方客户端，账号仍可能被要求验证。
- 微信主程序走 MMTLS + protobuf，且每个版本会变；维护一个自定义客户端需要持续逆向，成本远高于微信读书 E-Ink 的 `/mp/chapters`。
- 现实证据：本项目对微信读书 E-Ink 已经做了设备型号、appver、basever、UA、deviceId/installId 等模拟，仍然会出 `-2041`（909705585 定时同步成功率约 51%，938161607 长期 HUMAN_VERIFY，Web 账号累计 213 次频控）。微信主程序的风控只会更强。

**Windows 微信 hook（你说得对，确实有专门的公众号历史采集方案）**：

- 开源社区里有一类项目专门做这件事：通过 DLL 注入 Windows 微信，hook 客户端“打开 URL / 内置浏览器”的关键调用，让官方客户端自己打开公众号主页/历史页，然后从内存或回调里取出 `key`、`uin`、`pass_ticket` 等会话参数，再按 `profile_ext/getmsg` 或 `getmsg0` 分页回放，从而拿到历史文章列表和 `content_url`。
- 代表项目/思路（仅列名，不复述偏移和利用代码）：
  - `xCss/wechat-mp-harvest`：面向微信 PC 4.1.8.107，DLL hook + profile URL dispatch + 内存扫描 + `getmsg0` 回放，README 明确写“Full article history extraction / unlimited pagination”。
  - `ljc545w/ComWeChatRobot`：较早的 PC 微信 COM/DLL hook，2022-09 更新记录里明确加了“获取公众号历史消息功能”，并自己注明“具体能获取多少未测试，请谨慎使用，以防封号”。
  - `redtips/wechathook`：更老的 2.6.8.52 方案，hook 关键 call 后把数据交给 Python 爬取。
  - `WeChatFerry`：聊天机器人生态很大，但公众号历史本身不是它的内置能力（相关 issue 被关闭为 not planned）；历史采集通常是另外的 hook/回放方案。
- 这些方案的本质是“用真实 Windows 微信客户端拿到合法会话参数，再回放历史接口”，所以它确实比自建 MMTLS 客户端更接近“官方会话”，能减少一部分设备/协议指纹问题。
- 但它们仍有明显代价：
  - 强绑定 Windows 微信版本（4.1.8.107、3.7.0.30 等），客户端一升级就要重新找偏移/适配；
  - 需要 Windows 机器/VM、真实登录的微信账号、DLL 注入权限；
  - 回放历史接口仍会触发服务端风控，ComWeChatRobot 自己都提示可能封号；不是“零验证码”；
  - 第三方 DLL 有窃取凭据/聊天记录、供应链投毒风险；违反微信服务条款，账号可能被封。
- Linux 侧：原生 Linux 微信 4.x 的 hook 项目更少，且大多不是为公众号历史设计；常见做法是 Wine/容器跑 Windows 微信 + Windows hook（如 WeChatFerry 的 Docker 方案），本质仍是 Windows hook，版本锁定和封号风险一样存在。

**如果要在本项目里验证 Windows hook，建议的路径**：

1. 隔离环境：单独的 Windows 10/11 VM，固定微信版本，专用可丢弃微信号，不要和现有生产微信/微信读书账号混用。
2. 小流量：先只抓 1 个公众号、每天 1 页，观察 3–7 天；再逐步到 5–10 页/天，记录 `验证码次数/千次请求`、`封号/强制下线次数`。
3. 只做实验通道：通过本地 HTTP/命名管道桥接到现有 MQ，不直接替换 WeRead E-Ink 主链路；失败可随时摘除。
4. 成本核算：Windows VM + 固定版本客户端 + 人工维护偏移，按“每万篇文章的账号/维护成本”和 WeRead E-Ink 对比，再决定是否值得上线。

**更现实的“慢而稳”方案**：

1. 微信读书 E-Ink `/mp/chapters` 为主：一 vid 一客户端，按时间范围截断分页，8–12 秒/请求 + 抖动，缓存优先。
2. 微信读者侧历史只作为兜底：真实设备 + 官方微信客户端 + 人工节奏的 UI 自动化（项目已有 AAOS 兜底），接受偶尔人工验证，而不是追求零验证码。
3. 多账号/多设备池 + 验证码恢复流程（自动解题 + 人工兜底），把“验证码率/千次请求”和“账号封禁率”作为可运维指标。
4. 不建议把自建 MMTLS 客户端或 hook 作为主链路；如果要做 Windows hook 实验，只作为独立实验通道（隔离 Windows VM + 一次性账号），先测“每千次请求验证码率/封号率”，不要直接接生产 MQ。

### 2.6 Root 现状与边界（2026-11-12 核实）

现场 ADB 检查结果：

```text
adb root                          -> adbd cannot run as root in production builds
adb shell su -c id                -> /system/bin/sh: su: inaccessible or not found
ls /data/adb/ksu/bin/su           -> Permission denied
ls /data/adb/magisk/su            -> Permission denied
ro.debuggable=0, ro.boot.verifiedbootstate=green, ro.boot.flash.locked=1
```

结论：设备上确实存在 `/data/adb/ksu/bin/su` 和 `/data/adb/magisk/su`，但 `/data/adb` 对 `shell` 用户不可读，ADB shell 没有拿到 root；当前 root 只授权给 App，未授权给 `com.android.shell`。如果要在 ADB 侧使用 root，需要在 Root 管理器里给 `com.android.shell` 授权，或安装一个 root 终端 App。

**Root 能做什么、不能做什么**：

- 能做：读取 App 沙箱、数据库、缓存、`shared_prefs`；安装系统 CA；做自己 App 的动态分析/备份。
- 不能做：把“验证码环境”整体复制到 Linux。验证码是服务端按账号、设备、IP、行为、会话综合判定的，不是本地一个静态目录；复制设备标识/令牌反而可能触发“新设备/多设备”风控，甚至让手机端会话失效。
- 微信 MMTLS + 证书固定 + 反调试会让抓包/取密钥变成持续对抗；即使拿到会话参数，从 Linux 回放也大概率被要求验证。
- 因此本文不提供提取微信会话密钥/Cookie 或克隆验证码环境的步骤；这类操作属于绕过安全控制，账号封禁和合规风险都很高。若要做研究，应使用隔离环境、一次性账号，并只做非敏感的协议/行为分析。

### 4.3 关键风险点

1. **同一 vid 被手机和服务器同时使用**：手机 App 数据库路径是 `databases/909705585/...`；服务器 E-Ink 的 `active_vid` 也是 `909705585`。这是需控制验证的混杂因素，目前没有因果证据。

3. **E-Ink 全量回扫过多**：单次任务常见 `pages=3/5/6/10`，`fetched=200~495`；对“某段时间”任务来说，命中起始时间后应立刻停止，而不是继续把历史翻完。

## 5. 收益判断

### 5.1 已经确认的收益

- **取链方式观察**：APK与本次已有观测支持从 `/mp/chapters` 列表获取文章标识和链接字段；实际响应字段仍需fixture验证，不能据此断言每种返回都无需回填。
- **不需要手机 UI 自动化**：手机 App 的“目录”列表本质上也是 `/mp/chapters`，用服务器 API 复现即可，没必要用无障碍点击。
- **不需要 `pass_ticket`**：`pass_ticket` 只是微信 WebView 的会话票据，不能复用到服务器；链接本体不含它也能访问。
- **分页实现方向**：首屏请求、offset续页和按 `createTime` 截断都由代码支持；`hasMore`、`nextOffset`与结束语义需真实响应核实。

### 5.2 可进一步获得的收益

- **降低请求量**：按目标任务的时间范围截断，通常 1–2 页即可覆盖一个月，避免每次 5–10 页。
- **降低 `-2041` 概率**：App 的请求节奏是“打开目录时拉一页，滚动再拉下一页”，不是后台连续翻 10 页；把服务器同步改成“按需分页 + 长间隔”更接近真实行为。
- **设备身份隔离**：如果服务器必须用 E-Ink，最好给服务器一个独立的 vid/设备身份；不要和手机共用 909705585。
- **`mobileSync` 可选实验**：在独立账号上开启 `mobile_sync_activation`，模拟 App 启动时的终端激活，可能降低 `-2041`；但必须小范围、可回滚，不能全局打开。

## 6. 降低风控的可执行建议

### P0（优先做，风险最低）

1. **一 vid 一客户端**
   - 手机 App 使用 `909705585`；
   - 服务器 E-Ink 改用另一个独立账号（例如恢复 `938161607`，或新开第三个墨水屏账号）；
   - 不要在服务器和手机同时跑同一个 vid；如果必须共用，至少保证同一时间只有一个客户端在请求。
2. **任务按时间范围截断**
   - 命中 `createTime <= 目标开始时间` 立即停止翻页；
   - 后台历史扫描仍可用 `max_pages: 1000`；实时补链另有 `targeted_max_pages: 20` 预算；
   - 优先命中本地缓存和覆盖度，不要每次任务都全量回扫。
3. **不要为整个列表逐篇 `/review/single`**
   - 继续使用列表里的 `doc_url` / `originalId` / `reviewId`；
   - `doc_url` 缺失时先尝试缓存、`originalId` 与 `reviewId`短链；仍无法映射才调用 `/review/single`；
   - 用 `review_single_backfills` 观察实际调用，不用 `skipped` 推断调用数。

### P1（建议尽快做）

4. **Web验证恢复与频控分别处理**
   - 人工确认 `-2041` 已恢复后立即重新调度，不再加恢复等待或额外探测门槛；
   - 新发生的 `-2014` 使用本地 `freq_control_cooldown: 1200`；
   - 频控返回的空列表不能当作“覆盖完成”，应标记为未覆盖并走 E-Ink/缓存。
5. **E-Ink 请求节奏**
   - `weread.eink.min_request_interval` 本地值设为 10 秒（代码仍有硬下限和随机长停顿）；
   - 避免健康探测和后台同步在同一 vid 上紧邻发生；
   - `-2041` 后 E-Ink 真实探测间隔本地设为 7200 秒；Web 验证成功后立即恢复调度，后续 -2014 仍按现有冷却策略处理。
6. **分页参数与 App 对齐**
   - 首次无历史游标请求 `bookId + count`；有效增量游标继续使用 `synckey`；
   - 需要翻页时用 `offset`；
   - 只有在确认 `synckey` 增量语义可靠时才使用增量同步。

### P2（需要小范围验证）

7. **`mobileSync` 终端激活实验**
   - 仅在独立 E-Ink 账号上开启，`vid_allowlist` 只放该账号；
   - 先补齐 App 2.1.2 的请求字段（当前 App 的 `mobileSync` 还包含 `storyfeed`、`eink_new`，服务器 `MOBILE_SYNC_BODY` 没有这两个字段）；
   - 记录激活前后 `-2041` 次数、成功率和恢复耗时，失败立即回滚。
8. **监控指标**
   - 每 vid：成功/失败、`-2041` 次数、平均恢复耗时、每日请求页数；
   - Web：`-2041` 次数、频控次数、冷却时长、空列表比例；
   - 以“每万篇文章的请求数”作为优化目标，而不是单纯追求翻页速度。

## 8. 不建议做的事

- **不要把 `pass_ticket` / `exportkey` 写入配置或数据库**：它们是微信会话票据，短时有效且高敏。
- **不要用手机无障碍去逐篇点开文章取链接**：列表接口已经直出链接，UI 自动化只会更慢、更容易触发风控。
- **不要在同一个 vid 上同时跑服务器同步和手机 App**：这是当前最可疑的风控触发源之一。
- **不要用“频控空列表”判定覆盖完成**：会把缺口误标成 EMPTY，后续任务不再回源。
- **不要把 `mobile_sync_activation` 全局打开**：先用独立账号 + allowlist 做 A/B，观察 `-2041` 和成功率后再决定。
