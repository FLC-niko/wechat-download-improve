# we-mp-rss-kotlin × wechat-download-api 深度整合设计

> 目标：让现有 Kotlin Worker（we-mp-rss-kotlin）以「深度整合」方式消费 wechat-download-api 的抓取与本地存储能力。
> 原则：Worker 不再自建文章文件存储，改为消费 wechat-download-api 的 SQLite 本地库与既有抓取轮询，最小化重复逻辑。

---

## 1. 背景与现状

### 1.1 现有 Kotlin Worker 依赖的后端接口（we-mp-rss 后端协议）

Worker 通过 `AuthApi` / `MpApi` / `ArticleApi` 调用后端，均带 `Authorization: Bearer <token>`：

| Worker 调用 | 用途 |
|---|---|
| `POST /api/v1/wx/auth/login` | 账号密码换 access_token |
| `GET /api/v1/wx/auth/qr/code` `/qr/status` `/qr/confirm` | 扫码登录 |
| `GET /api/v1/wx/mps?limit&offset&kw` | 公众号列表 |
| `POST /api/v1/wx/mps` | 添加公众号 |
| `GET /api/v1/wx/mps/search/{keyword}` | 搜索公众号 |
| `GET /api/v1/wx/mps/update/{mpId}?start_page&end_page` | 触发刷新 |
| `GET /api/v1/wx/articles?mp_id&limit&offset` | 分页拉文章列表 |

响应统一 `{code, message, data:{list,total}}`，`code==0` 成功。

### 1.2 Worker 当前存储方式

`GzhTaskDispatcher` + `ArticleFileRepository`：
- Worker 把后端当「抓取执行器」，自身把文章写成本地 JSON 文件（`{公众号名}_articles.json`）。
- 输出格式见 `ArticleModels.kt`：`ArticleOutput{ metadata, articles[] }`。
- 文章元数据字段：`id / title / url / publish_time / publish_date`。

### 1.3 wechat-download-api 能力

| 接口 | 用途 |
|---|---|
| `GET /api/public/searchbiz?query=` | 搜索公众号 → fakeid |
| `GET /api/public/articles?fakeid&begin&count&keyword` | 文章列表分页 |
| `POST /api/article` | 单篇全文解析 |
| `POST /api/rss/subscribe` `GET /api/rss/{fakeid}` | 订阅 / RSS |
| `POST /api/rss/poll` | 手动触发全局轮询 |
| `GET /api/feed/articles.json?since&fakeid&limit` | **本地库增量拉取（含 id）** |
| `GET /api/feed/article/{id}.md` | **本地库单篇正文 markdown** |
| `POST /api/login/*` | 公众号管理员扫码登录（token+cookie 存 `.env`） |

存储：SQLite（`data/rss.db`），核心表：
- `subscriptions(fakeid, nickname, alias, head_img, last_poll, ...)`
- `articles(id, fakeid, aid, title, link, digest, cover, author, content, plain_content, publish_time, source, fetched_at, UNIQUE(fakeid,link))`

轮询：`rss_poller` 定时（默认 3600s）拉全部订阅号文章元数据进库，可选全文（`RSS_FETCH_FULL_CONTENT`）。

## 2. 整合方向（B：深度整合）

核心决策：**以 wechat-download-api 的 SQLite 库为唯一文章存储，Worker 退化为「消费本地库 + 发布结果到 MQ」的薄客户端。**

- 抓取（列表 + 全文）→ 交给 wechat-download-api 的 `rss_poller`（已具备反风控）。
- 存储 → 交给 SQLite `articles` 表（已具备）。
- Worker 通过 `feed` 接口增量读取本地库，生成结果发布到 MQ（复用现有 `ResultQueuePublisher`）。

这样去掉了 Worker 的 `ArticleFileRepository` 本地 JSON 文件存储与「触发后端刷新」逻辑，避免两套存储双写。

---

## 3. 适配层设计（在 wechat-download-api 上新增 `/api/v1/wx/*`）

### 3.1 鉴权

新增 `POST /api/v1/wx/auth/login`：校验内置密钥（`ADAPTER_API_KEY`），返回固定 `access_token`，供 Worker `getAccessToken()` 直接通过。

### 3.2 路由映射

| Worker 期望 | 适配实现 | 说明 |
|---|---|---|
| `POST /api/v1/wx/auth/login` | 校验 `ADAPTER_API_KEY`，返回 `{code:0,data:{access_token}}` | 不再走公众号后台扫码鉴权 |
| `GET /api/v1/wx/mps/search/{kw}` | 调 `/api/public/searchbiz`，`fakeid→id`、`nickname→mp_name`、`round_head_img→mp_cover` | 返回 `{code:0,data:{list}}` |
| `GET /api/v1/wx/mps?limit&offset&kw` | 从 `rss_store.list_subscriptions()` 读，支持 kw/分页 | 返回 `{code:0,data:{list,total}}` |
| `POST /api/v1/wx/mps` | 映射 `/api/rss/subscribe`（若只有名称，先 searchbiz 取 fakeid） | 返回新订阅 |
| `GET /api/v1/wx/articles?mp_id&limit&offset` | 调 `feed/articles.json`（fakeid=mp_id）或按分页查询 `articles` 表 | 字段映射：`publish_time` 直用；`url`←`link`；`id`←`id` |
| `GET /api/v1/wx/mps/update/{mpId}?start_page&end_page` | 触发**单号**抓取（见 §4） | 这是最大差异点 |

### 3.3 字段映射

- 公众号 ID：`fakeid` ↔ `mp_id`
- 公众号名：`nickname` ↔ `mp_name`
- 头像：`round_head_img` ↔ `mp_cover`
- 文章：`link` ↔ `url`；`publish_time` 一致；`id` 一致

## 4. 「触发刷新」差异处理（关键决策点）

Worker 的 `refreshMpArticlesWithPagination` 依赖 `start_page / end_page` 分页语义，而 wechat-download-api 的 `rss_poller` 是**全局全量**轮询。

深度整合方案：
- 在 wechat-download-api 新增**单号即时抓取**能力（`rss_poller` 增加 `poll_single(fakeid, start, end)`，复用现有 `_fetch_article_list` + `_enrich_articles_content`），并把 `begin/count` 分页参数传入微信 `appmsgpublish`。
- 适配壳 `GET /api/v1/wx/mps/update/{mpId}` → 触发 `poll_single`，把 `start_page/end_page` 换算为 `begin/count`。
- 之后 Worker 再走 `GET /api/v1/wx/articles` 消费落库结果。

> 若接受「按轮询间隔批量更新」，可简化为：适配壳仅触发一次 `rss_poller` 全局轮询，`start_page/end_page` 参数忽略。为最小改动可先采用此简化版，后续再加单号精确抓取。

---

## 5. Worker 侧改动点（深度整合后）

1. `ArticleFileRepository`：不再负责写本地 JSON 文件与发布；文章数据改为从 `feed/articles.json` 读取。
2. `GzhTaskDispatcher` / `doFetchAndSave`：把「触发后端刷新 + 写文件」改为「触发适配壳 update → 读 feed/articles.json → 组装结果发布 MQ」。
3. `SyncStateManager`：`fetched_page_ranges` 语义简化（分页由 wechat-download-api 管理）。
4. `ArticleOutput` 生成逻辑保留，但 `articles` 来源变为 SQLite 查询结果。

> 注意：需保留 Worker 的 MQ 消费/发布协议（`GzhTaskDispatcher` 对 `GZH_TASK_QUEUE` 消费、`ResultQueuePublisher` 发布）不变，只替换数据来源。

---

## 6. 数据流（整合后）

```text
RabbitMQ GZH_TASK_QUEUE
   │  (Worker 消费任务)
   ▼
Kotlin Worker
   ├─ getAccessToken() ──> POST /api/v1/wx/auth/login (适配壳)
   ├─ search/add mps ────> /api/v1/wx/mps* (适配壳 ──> searchbiz / rss.subscribe)
   ├─ update {mpId} ─────> /api/v1/wx/mps/update/{mpId} (适配壳 ──> rss_poller.poll_single)
   └─ read articles ─────> /api/v1/wx/articles (适配壳 ──> SQLite articles 表)
                                    │
                              wechat-download-api
                               ├─ SQLite data/rss.db (唯一存储)
                               └─ rss_poller 定时 + 反风控抓取
                                    │
                              ResultQueuePublisher ──> RabbitMQ 结果队列
```

## 7. 风险与边界

- **单公众号登录态**：wechat-download-api 用一个公众号管理员微信扫码，凭证 4 天过期；需保留 `login_reminder` Webhook 预警（已内置）。
- **反风控是否够用**：这是替代方案的核心假设，需实测验证（见 §8 验证清单）。
- **AGPL-3.0**：自托管 API 服务方式使用影响可控，但若闭源分发需评估合规。
- **字段语义简化**：Worker 原有 `fetched_page_ranges`、`server_refreshed_this_time` 等元数据在新模式下无对应物，需降级/移除。

3. 跑 1–2 周观察 `rss_poller` 稳定性、登录态存活、反风控是否扛得住。
4. 确认 SQLite `articles` 表能稳定积累目标公众号文章。
5. 验证 `feed/articles.json` 增量接口可用作 Worker 数据源。

验证通过后再实施 §3/§5 的适配壳与 Worker 改造。
