## 处理链路

| 请求/状态 | 实际采用的结果 |

| 文字题 A 组 | 应用机原 9993 |
| 文字题 B 组，5090 可达且模型正确 | 5090 GPU 融合，经应用机回环 9996 私有隧道 |
| B 组远端超时、断线、繁忙、模型版本不符 | 应用机 9994 同版 CPU 融合 |
| B 组本机融合也异常 | 应用机原 9993 |
| 比例归零或配置缺失/损坏 | 全部旧版结果 |

应用机保留旧模型、CPU 融合模型及所有运行依赖，5090 不是必需依赖。
远端与本机融合使用同一 run-03 模型制品，指纹 `6cc80d5cde1b81ec`；提升来源是
融合模型，GPU 提供可选加速，并不意味着 GPU 比同版 CPU 模型准确。

路由先取得旧版结果作为兜底，B 组再尝试融合。远端超时 2.5 秒，本机融合超时
4 秒；远端失败后熔断 30 秒，之后允许重试。远端单路并发，忙时立即走本机，
避免在 5090 排长队。原服务本身异常仍会报错，不保证本机所有服务同时损坏时可用。

应用机 `eink-text-shadow`（9995）现执行 `text_ab_router.py`，配置为
`/home/topview/captcha/text-ab.json`，每次请求读取，修改比例不需要重启。
本机原服务 9993、同版 CPU 融合 9994 及调度服务 9991 均保留。

## 已完成验证

- 22 项相关测试通过，覆盖超时回退、熔断恢复、模型版本拒绝、繁忙回退、
  本机融合故障、错误配置恢复旧版、稳定分组、回放排除、观测去重及配置恢复。
- 初次 GPU 验收发现 TF32 引起融合分数变化，未据此放量。关闭 TF32 后重新验证，
  10/10 真实图片的选格和 OCR 相同，融合分数最大差约 `2.28e-4`（验收阈值 `1e-3`）。
  预热后 GPU 端到端隧道请求约 0.12–0.19 秒；首次冷推理约 2.37 秒。
  这些是推理一致性和耗时检查，不能算独立准确率评测。
- 在隔离入口实际切断新增隧道，B 组成功返回本机 CPU 融合，耗时约 2.24 秒。
  隔离本机融合端点也不可用时，成功返回真实旧服务结果，约 0.75 秒。
- 正式 0% 入口和旧服务返回 JSON（去除新增 `ab` 字段）逐字段相同。
- 正式 10% 自然分组的 A/B 各验证一题；实际完成 **10% → 0% → 10%**，
  原 B 题归零后返回旧版，恢复后重新采用 GPU 融合。均标记为 replay，不混入线上数据。

## 线上观测与放量

每次文字题响应增加 `ab` 字段，记录阶段、分组、实际服务、回退原因、模型指纹和耗时；
不含账号、ticket 或 randstr。路由事件在
`/home/topview/captcha/text-ab-events.jsonl`，每份 10 MiB，保留 5 份轮转备份。
`GET http://127.0.0.1:9995/health` 提供当前比例、熔断状态和本进程各路线上请求计数。
该请求计数跨放量阶段累计；下面的验证结果汇总按当前比例单独统计，两者口径不同。

已有 daemon 的 `DEBUG_SAVE=1` 继续记录选格和验证结果，无需改动或重启 daemon。
新增 `eink-text-ab-outcomes.timer` 每分钟将已有的 pick 与 verify-outcomes 按轮次关联，
汇总到 `/home/topview/captcha/text-ab-outcomes.json`，区分 A 旧版、B GPU、B CPU
与 B 旧版兜底，只统计本阶段 live 记录及其 `ab.percent` 与当前配置一致的轮次。
10% 和 50% 的验证结果不混算；历史明细保留，需要时可另行回溯。

汇总中 errorCode=0 记为已接受；其他代码可能包含网络、会话与限流因素，不能全部
当成识别错误，也不自动变成人工标签。低置信度跳过、未提交、无验证响应的轮次不在
已观察响应的接受率分母内，因此需结合路由请求计数看待。重复图片重试也不独立。
旁路人工队列继续保留，模型预测始终不是人工真值。
